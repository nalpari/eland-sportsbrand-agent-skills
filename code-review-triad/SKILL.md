# 3관점 PR 리뷰 (Sonnet ×3 → Opus 종합) → 머지 블로커 코멘트

| 역할 | 주체 | 하는 일 |
|------|------|---------|
| 리뷰어 | Sonnet 서브 에이전트 3개 | 퍼포먼스 / 문법·정확성 / 시큐리티 관점으로 각자 리뷰 |
| 판정자 | Opus 서브 에이전트 1개 | 세 결과를 검증·종합해 머지 블로커만 남기고 해결 방안을 붙인다 |
| 진행자 | 이 세션 | worktree 준비, 서브 에이전트 실행, 표 보고, 승인 후 코멘트 등록 |

진행자는 **리뷰도 판정도 하지 않는다.** 종합 판단을 Opus 서브 에이전트에 맡기는 이유는
세션이 어떤 모델로 돌든 판정 품질이 같아야 하기 때문이다. 진행자가 항목을 더하거나
빼면 그 보장이 깨진다.

모델은 Agent 툴의 별칭(`"sonnet"`, `"opus"`)으로 지정한다. 별칭은 사용 가능한 최신
버전(작성 시점 Sonnet 5.5 / Opus 5.5)으로 풀린다. 버전 번호는 지정할 수 없다.

## 입력

- **PR 번호** — 필수. 없으면 물어본다. 추측하지 않는다.

## 절차

### 1. PR 메타 확인

```bash
gh pr view <n> --json number,title,url,state,baseRefName,headRefName,headRefOid
```

- `state` 가 `OPEN` 이 아니면 멈추고 알린다. 닫히거나 머지된 PR 에 블로커 코멘트는 의미가 없다.
- `baseRefName` 이 base, `headRefOid` 가 리뷰 대상 커밋이다.

### 2. 임시 worktree 준비

사용자의 워킹 트리와 브랜치는 **건드리지 않는다.** 따로 풀어서 읽는다. 그래서 워킹
트리가 더러워도 멈출 이유가 없다.

```bash
git fetch origin <baseRefName>
git fetch origin "pull/<n>/head"
WT=$(mktemp -d)/pr-<n>
git worktree add --detach "$WT" FETCH_HEAD
git -C "$WT" rev-parse HEAD
```

- fetch 를 둘로 나누는 이유: 한 번에 두 ref 를 받으면 `FETCH_HEAD` 가 첫 번째(base)를 가리켜 base 를 리뷰하게 된다. PR head 를 반드시 마지막에 받는다.
- `pull/<n>/head` 를 받는 이유: 포크에서 온 PR 도 같은 방법으로 받힌다. 브랜치 이름으로 받으면 포크 PR 을 놓친다.
- `rev-parse` 결과가 `headRefOid` 와 다르면 그 사이 푸시가 있었던 것이다. 실제로 받은 SHA 를 리뷰 대상으로 삼고, 보고와 코멘트에 그 SHA 를 적는다.
- 리뷰 범위는 `git -C "$WT" diff origin/<baseRefName>...HEAD` 다.

**worktree 는 6단계에서 반드시 지운다.** 중간에 실패하거나 사용자가 멈춰도 지운다. 남겨 두면 `git worktree list` 에 쌓이고 같은 PR 을 다시 돌릴 때 충돌한다.

### 3. 리뷰 서브 에이전트 3개 실행

Agent 툴로 `subagent_type: "general-purpose"`, `model: "sonnet"` 서브 에이전트 3개를 **한 메세지에서 동시에** 띄운다. 서로 의존이 없으니 순차로 돌리면 시간만 세 배다.

공통 프롬프트:

```
PR #<n> 이 origin/<base> 에 머지되기 전이다. <관점> 관점으로 리뷰해라.

코드 위치: <WT>   (PR head 가 풀린 worktree. 이 경로 안에서만 읽는다)
대상 diff:  git -C <WT> diff origin/<base>...HEAD

<WT>/CLAUDE.md 가 있으면 먼저 읽는다. 거기 적힌 프로젝트 규칙 중 이 관점에 해당하는
것을 위반한 코드도 지적 대상이다. 위반이면 어느 절의 규칙인지 적는다.

찾을 것 — 머지 후 프로덕션에서 실제로 터지는 것만:
<관점별 공격 지점>

규칙:
- diff 에 실제로 있는 코드만 지적한다. 기억이나 추측으로 코드를 만들어내지 마라.
- 지적할 때마다 해당 파일을 직접 열어 주변 맥락(호출부 포함)을 확인한다.
- 스타일·네이밍·취향·"이렇게 하면 더 좋다" 류 제안은 보고하지 마라.
- 파일을 수정하지 마라. 읽기만 한다.

각 지적을 이 형식으로 반환한다:
  위치: <파일:줄>   (worktree 루트 기준 상대 경로)
  문제: <한 줄>
  실패 시나리오: <어떤 입력/상태 → 어떤 잘못된 결과>
  근거: <해당 코드 인용>
지적할 게 없으면 "없음" 이라고만 답한다.
```

관점별 공격 지점:

| # | 관점 | 공격 지점 |
|---|------|-----------|
| 1 | 퍼포먼스 | N+1 쿼리, 루프 안 I/O·네트워크 호출, 핫 경로의 O(n²) 이상, 페이지네이션 없는 전체 조회, 종료 조건 없는 루프·재귀, 해제 안 되는 리스너·타이머·구독, 무한히 자라는 캐시·컬렉션, 요청 경로의 동기 블로킹 호출 |
| 2 | 문법·정확성 | 빌드·타입 체크를 깨는 코드, API 오용(시그니처·반환값 오해, `await` 누락, 잘못된 인자 순서), 타입 불일치, null/undefined 역참조, 항상 참·거짓인 조건, 리팩터링 중 깨진 호출부, 삼켜지는 에러 |
| 3 | 시큐리티 | 인증·인가 우회, 인젝션(SQL·명령·경로), 입력 검증 누락, 비밀값 하드코딩·로그 노출, XSS·CSRF·SSRF, 안전하지 않은 역직렬화, 권한 상승 |

퍼포먼스와 문법 관점을 "장애급" 으로 좁혀 둔 이유: 이 스킬의 산출물은 머지 블로커뿐이다. 마이크로 최적화나 리팩터링 제안을 찾게 하면 판정자가 전부 버리게 되고, 버릴 것이 많을수록 진짜 블로커가 묻힌다.

결과가 "없음" 으로 와도 그대로 받는다. 진행자가 대신 리뷰해서 채우지 않는다.

### 4. 판정 서브 에이전트 실행

Agent 툴로 `subagent_type: "general-purpose"`, `model: "opus"` 서브 에이전트 1개를 띄운다. 3단계의 세 결과를 **원문 그대로** 넘긴다. 진행자가 요약하거나 거르면 판정자가 볼 것을 진행자가 대신 고른 셈이 된다.

```
PR #<n> (base: origin/<base>, head: <SHA>) 에 대한 리뷰 결과 3건이다.
코드 위치: <WT>   대상 diff: git -C <WT> diff origin/<base>...HEAD

[퍼포먼스]
<원문>
[문법·정확성]
<원문>
[시큐리티]
<원문>

이 중에서 머지 블로커만 골라라. 아래를 전부 만족해야 블로커다.
- diff 에 실제로 있는 코드다. 인용된 줄을 <WT> 에서 직접 열어 확인한다. 없거나 인용과 다르면 버린다.
- 구체적 실패 시나리오가 성립한다. 어떤 입력/상태 → 어떤 잘못된 결과인지 쓸 수 있다.
- 그 실패가 머지 후 프로덕션에서 터지거나 데이터·보안이 깨진다.

나머지는 전부 버린다. major / minor / 취향 / 리팩터링 제안은 남기지 않는다.
같은 문제를 둘 이상이 지적했으면 한 줄로 합친다. 중복 지적이 심각도를 높이지는 않는다.
직접 새 항목을 찾아 더하지 않는다. 판정만 한다.
파일을 수정하지 않는다.

각 블로커에 추천 해결 방안을 한 줄로 붙인다. 코드가 아니라 무엇을 어떻게 바꾸면 되는지다.

반환 형식: 아래 마크다운 표만. 블로커가 없으면 "블로커 없음" 한 줄만.
| # | 관점 | 위치 | 문제 | 실패 시나리오 | 추천 해결 방안 |
```

판정자에게 새 항목 추가를 막는 이유: 판정자가 리뷰까지 하면 세 관점으로 나눈 구조가 의미를 잃는다. 판정자의 가치는 검증과 선별이다.

### 5. 보고와 승인

판정 표를 사용자에게 그대로 보여주고, **등록할지 묻는다.** 승인을 받기 전에는 등록하지 않는다. PR 코멘트는 팀 전체에 알림이 가는 외부 행위라 등록한 뒤에는 되돌릴 수 없다. 오탐을 사람이 거를 마지막 기회다.

- 사용자가 특정 항목을 빼라고 하면 빼고 등록한다.
- 사용자가 등록하지 말라고 하면 등록하지 않고 6단계로 간다.

승인되면 본문을 heredoc 으로 임시 파일에 쓰고 넘긴다. `--body` 에 여러 줄 마크다운을 인라인으로 넣으면 셸 이스케이프가 깨진다.

```bash
gh pr comment <n> --body-file <파일>
```

### 6. 정리

```bash
git worktree remove --force "$WT"
```

1~5단계 어디서 멈췄든 worktree 를 만들었다면 이 단계는 실행한다.

## 코멘트 형식

```markdown
## 🚫 머지 블로커 (code-review-triad · `<SHA 앞 7자리>`)

| # | 관점 | 위치 | 문제 | 실패 시나리오 | 추천 해결 방안 |
|---|------|------|------|---------------|----------------|
| 1 | 퍼포먼스 | `src/order.ts:42` | 루프 안에서 주문마다 조회 | 주문 1,000건 → 쿼리 1,000회, 응답 타임아웃 | `IN` 조회 한 번으로 묶고 맵으로 매칭 |

블로커 N건. 전부 해결 전에는 머지하지 않는다.
```

블로커가 0건이면 표 없이 한 줄만 등록한다.

```markdown
✅ 머지 블로커 없음 (code-review-triad · `<SHA 앞 7자리>` · 퍼포먼스 / 문법·정확성 / 시큐리티)
```

- SHA 를 적는 이유: 이후 푸시가 있으면 코멘트가 어느 시점의 판정인지 알 수 없게 된다.
- 셀 안에서 줄바꿈하지 않는다. 표가 깨진다. 길면 `<br>` 를 쓴다.
- 위치는 반드시 `파일:줄`. "인증 로직 부근" 은 위치가 아니다.

**파일을 고치지 않는다.** 이 스킬의 산출물은 코멘트다. 수정은 사용자가 따로 요청할 때 진행한다.

## 하지 말 것

- 사용자 워킹 트리에서 체크아웃하거나 stash 하기. 리뷰는 worktree 안에서만 한다.
- worktree 를 남기고 끝내기. 실패로 끝나도 지운다.
- 진행자가 직접 리뷰하거나 판정하기. 세션 모델이 Opus 가 아니면 판정 품질이 조용히 떨어진다.
- 리뷰 결과를 요약해서 판정자에게 넘기기. 원문을 넘긴다.
- 리뷰 서브 에이전트를 순차 실행하기. 한 메세지에 3개를 같이 띄운다.
- 인용된 줄을 확인하지 않은 항목을 표에 올리기. 없는 코드를 지적한 코멘트는 신뢰를 통째로 날린다.
- 승인 없이 코멘트 등록하기.
- 대상 저장소 `CLAUDE.md` 의 규칙 내용을 이 파일에 복사하기. 원본이 바뀌면 조용히 어긋난다. 서브 에이전트가 매번 직접 읽는다.
